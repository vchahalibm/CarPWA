The full product is thousands of combinations; we test the network pairs exhaustively in the lab (cheap, automated), the most common real pairs every night, and the rest in field sessions.

3. Four layers of testing

 Layer 1  Connection test screen (in both apps)   → anyone can run it anywhere; a report to share
 Layer 2  Network lab on one Mac (Docker)         → every NAT/firewall pair, every setting, automated, minutes
 Layer 3  Real internet, nightly (GitHub Actions) → cloud peers ↔ the Mac at home, across real networks
 Layer 4  Field sessions on real devices          → carriers, hotels, offices, the car; a checklist

4. Layer 1: a Connection test screen in both apps

Settings › Connections › Test the connection, in DriveGen and StudioGen. It runs in about 20 seconds and shows, then copies as JSON (or shows as a QR for the other app to scan):

  • This network: local addresses (IPv4/IPv6), public address and port from two STUN servers, and the NAT type estimate (same public port from both: port-preserving; different: strict/symmetric), UDP reachable or not, a captive portal detected or not.
  • Rendezvous: each broker in the list: connects, echo time, blocked or not.
  • With the paired app (when paired): seen online, direct link tried (candidate types gathered: host / srflx / relay; which pair won), result (direct / relay / failed), round trip, a 200-row request timed, the link now in use.
  • Verdict in plain words: “Direct link works on this network”, “Your network blocks direct links: using the relays”, “The relays are blocked here: try Tailscale or a TURN server”.

The same checks run headless through test hooks (?linktest) so Layers 2 and 3 use exactly the code users run.

5. Layer 2: a network lab on one Mac (automated)

Docker (Colima or Docker Desktop) builds small virtual networks with a Linux “router” container in front of each app. The apps run as headless Chromium (Playwright): DriveGen as-is, StudioGen's link side through a test shim (the same js/relay.js, js/direct.js, js/link.js, with the desktop powers stubbed). The real public brokers and STUN servers are used through the routers' internet access, plus a local broker and TURN server for offline runs.

The run

  • A test runner (Node + Playwright) loops over router A × router B × settings × link (about 10 × 10 × 6 for the relay link, plus the QR-direct and Tailscale-off cases), and for each: pair, wait online, try direct, send requests (small, 200 rows, a 2-minute script), inject the events of section 8, and record the results (time to online, link used, direct or not and why, round trips, failover time, errors).
  • About 600 cells at ~30 s each, run in parallel 6 at a time: under an hour; a “smoke” subset (20 cells) runs in about 5 minutes after every change to the link code.
  • Output: tests/net/report.json and an HTML matrix like section 2, with each cell green/amber/red against the expected outcome, and a diff to the last run.

6. Layer 3: real internet, every night (GitHub Actions)

  • A scheduled workflow starts headless DriveGens on GitHub's runners (Linux, in Microsoft's cloud: a different network and NAT than the Mac's), pairs them with a test StudioGen (a packaged StudioGen on the Mac at home or a spare Mac, left running with a test profile and a test pairing), and runs the smoke set over the real internet: online time, direct or relay, round trips, failover with one broker blocked on the runner.
  • Also runner ↔ runner across two regions (two jobs) for the no-Mac case of the shim.
  • Results go to a GitHub issue or the run summary; a red result opens an issue. Public brokers' health is tracked over weeks (which ones fail, when), feeding the default list.

8. Events and failures to inject

  • Brokers: the first broker down for both; down for one side only; all down then one back; a broker that accepts but drops messages; slow broker (2 s).
  • Network: switch networks mid-request; 10 s outage; IP address change; loss and delay (bad link); UDP suddenly blocked after direct connected.
  • Apps: StudioGen restart; Mac sleep/wake; DriveGen to background and back; phone locked for 1 and 10 minutes; two DriveGens at once; a request while the Mac is busy with a script.
  • Security: a replayed message (must be dropped), a message under the wrong key (ignored), a revoked device trying (no answer), an old list revision (told to pair again), a tampered pairing code (rejected).

10. Phases

  1. T1 The Connection test screen and the ?linktest hooks (with a StudioGen link shim for headless runs). Usable right away for your own field tests.
  2. T2 The Docker lab: router profiles, the runner, the smoke set after every link change, the full matrix weekly, the HTML report.
  3. T3 The nightly GitHub Actions run against a test StudioGen; broker health history.
  4. T4 Field sessions F1–F8 with the checklist; results feed the expected matrix and the default broker list.
