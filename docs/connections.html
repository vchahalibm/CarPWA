Requests (offers, run a script, say something) take the first that is up: direct → relay → Tailscale. Each link carries the same requests, so nothing else changes when one goes away.

2. The relay link and its broker list

  • StudioGen is the master of the list: Settings › Connections › Relays: an ordered list of brokers (wss://host:port/path, optionally wss://user:password@… for your own), with a revision that goes up when the list changes. “Test them” connects to each and times an echo.
  • Pairing carries the list: the code (SG3…) holds a random room, a 256-bit key, the brokers in order and the revision. DriveGen only consumes it.
  • A changed list needs pairing again: StudioGen keeps each device's list (the one it paired with) and keeps talking to it on that list, so nothing breaks mid-show; both sides show “pair again to use the new relays” (StudioGen sends its current revision in every hello).
  • Encryption: AES-GCM with the pairing key; the topic (which encodes the direction) is authenticated data; each message has a timestamp (older than 2 minutes: dropped) and an id (duplicates from the other broker or replays: dropped). Brokers see a random-looking topic, ciphertext, sizes, times and IP addresses, nothing else.
  • Revoke deletes the device's room and key on StudioGen: it can no longer be understood or answered.

3. The failover protocol

Both apps must agree on brokers without a coordinator. The rule is the same on both sides and needs no extra messages:

 shared ordered list (from pairing):   L = [ b1, b2, b3, b4, … ]

 each side, continuously:
   health(b)  = up      when its OWN messages come back through b (it subscribes to both directions;
                         every hello, every 25 s, is also the echo test, so no extra traffic)
              = down    after 2 misses (no echo in 10 s, or the connection fails/closes twice)
              = unknown not tried yet / being retried
   window     = the first 2 brokers of L that are not down for me
   hello      = { …, use: window }            (sent on every broker it uses, every 25 s and at once on any change)
   active     = window ∪ (the other side's use, if not down for me)        (at most 3 connections)
   send       = on every active broker;  receive = from any (duplicates dropped by id)

 recovery:    a down broker is retried after 30 s, 60 s, 2 min, 4 min, then every 5 min (with jitter);
              when it echoes again it is "up" and, being earlier in L, comes back into the window:
              both sides move back to the preferred broker on their own.
  • A broker down for everyone: both sides see their echoes stop, both drop it, both take the next one in L: they converge within about 20 s, and the hello tells the other at once.
  • A broker blocked only on one network (the car's mobile operator blocks b2): the phone moves to [b1, b3]; its hello says so; the Mac adds b3 to what it sends on. They still share b1 and b3.
  • Every broker down: status says the relays can't be reached; retries continue; direct and Tailscale still work when available.
  • Tested: a list starting with a non-existent broker (both skip it within 12 s), and the phone alone losing EMQX (it moved to HiveMQ + Mosquitto, the Mac joined Mosquitto, requests kept working).

4. Direct when possible

  1. When a paired device says hello, StudioGen offers a direct link: it creates a WebRTC connection with a data channel, gathers its network candidates (its local addresses; with STUN also its public address), and sends the offer through the encrypted relay.
  2. DriveGen answers the same way (unless its owner turned direct links off). Both try every pair of candidates (ICE): same Wi-Fi works almost always; across networks it works when at least one side's router allows it (most home routers and many mobile networks; not two strict/carrier-grade NATs).
  3. The link is DTLS-encrypted by WebRTC itself; the requests then go straight between the two (lower latency, no broker involved). Keep-alive every 5 s; no sign of life for 20 s: closed.
  4. When it can't connect or drops, requests stay on the relay, and StudioGen tries again after 1, 2, 5, then every 10 minutes (or right away when the network changes).

Settings (StudioGen's, sent with each offer): Whenever possible (with STUN, across networks) · Only on the same network (no outside servers at all) · Never (relays only). STUN servers editable (defaults: Google, Cloudflare; they only tell each side its public address). An optional TURN server (yours) relays the encrypted traffic when nothing else connects. DriveGen can refuse direct links.

Staying a good citizen (so the traffic looks like the ordinary low-volume IoT use these brokers are for, not abuse): QoS 0, nothing retained, no wildcard subscriptions, at most 3 connections per app, one small hello every 25 s, keep-alive 60 s, reconnects with growing, jittered pauses, messages of a few kilobytes (results capped at 200 rows). These public brokers are offered for testing and make no promises; for dependable use add your own broker (a free tier of HiveMQ Cloud or EMQX Serverless takes a user and password, which the list supports) at the top of the list.

Sources consulted for candidates: mqtt.org public brokers wiki, EMQX: popular public brokers, EMQX public broker, lddgo MQTT list, Bevywise; the table is from our own tests.

7. A mesh of StudioGens and DriveGens

What it would enable

  • One phone or iPad driving several Stage screens (demo room, booth, wall), or several presenters' phones driving one.
  • DriveGen asking the right Mac: “run the sales report on the office Mac”, “ask the home Mac to …”, or whichever Mac has the capability (Excel, a database, a model).
  • Distributed demos: one script spanning devices (Mac A presents while Mac B crunches data and Mac C drives a browser), with results flowing back.
  • Team setups: colleagues' StudioGens offering each other scripts, data and tasks, with permissions.

Architecture (proposal)

            ┌──────────── mesh "Acme demo team" (id M, group key Kg, roster signed by owners) ────────────┐
            │                                                                                            │
   DriveGen (iPhone) ─┐        relay families (MQTT, Nostr…)  +  direct WebRTC links where possible        │
   DriveGen (iPad) ───┼──────►  group topic  T(M)        : presence, capabilities, broadcasts (Kg)         │
   DriveGen (car) ────┘         device topics T(M,dev)   : requests/answers to one device (pairwise keys)  │
                                                                                                           │
   StudioGen "Demo room"  (owner)    StudioGen "Office Mac"  (member)    StudioGen "Home Mac"  (member)    │
   offers: Stage, scripts            offers: Excel tasks, SQLite          offers: Shortcuts, files         │
            └────────────────────────────────────────────────────────────────────────────────────────────┘
  • Identity: every app makes a device key pair (signing + key agreement) on first start; its id is a hash of the public key. Names are labels, keys are identity.
  • The mesh: an id, a group key, a broker list (owner-master, as today), and a roster: devices with role and permissions, signed by an owner StudioGen. Joining = pairing with an owner (or with any member an owner allowed to invite).
  • Messages: broadcasts (presence, “what I offer”) encrypted with the group key on the mesh topic; requests to one device encrypted pairwise (keys from the two device keys) on that device's topic; everything signed by the sender, so members can't impersonate each other.
  • Directory: each StudioGen announces its capabilities (scripts it offers, task kinds, data sources, models, screens, busy/free); every member keeps a live roster: who's online, where, what they can do.
  • Addressing: by device (“Office Mac”), by role (“any Stage screen”), by capability (“a Mac with Excel”), or all (“every screen: next slide”).
  • Routing: the relay families reach everyone; direct WebRTC links form between pairs that talk a lot; a StudioGen can forward for a device that can't reach another directly.
  • Scripts across devices: a step gets a target (“on Office Mac: run Export”), results come back as variables; a “conductor” script can coordinate several Stage screens in sync.
  • Changes: removing a member, or a new broker list, rotates the group key and needs the remaining members to take the new roster (pairing again, as you asked for brokers, or an owner-signed update; see the questions).

Phases

  1. M1 Device identities; a DriveGen paired with several StudioGens; pick the Mac by name (“run … on the office Mac”).
  2. M2 Mesh with roster, group topic, presence and capability directory; addressing by role and capability.
  3. M3 Cross-device script steps, results as variables, StudioGen-to-StudioGen requests; per-device permissions.
  4. M4 Synchronised multi-screen scripts (a conductor); forwarding; Nostr as a second relay family.

8. Decided (18 Oct 2026)

  • Teams from the start: colleagues' StudioGens and DriveGens join a mesh; every device has its own identity and a role, with per-device permissions.
  • Any member with an invite admits: a member creates an invite (a signed, single-use, expiring token, shown as a QR code or sent as a link); the newcomer pairs with that member; the inviter signs the roster entry; owners can set who may invite and remove anyone.
  • Changes: broker-list and roster changes travel as owner-signed updates over the mesh (no re-pairing); removing a member rotates the group key and the remaining members take the new key (signed by an owner) or pair again. The simple one-to-one pairing keeps its rule: a new list means pairing again.
  • Two modes:
    • Request mode: run or ask by device or by capability (“run Export on the Office Mac”, “a Mac with Excel: …”); results come back.
    • Mesh mode: synchronised multi-screen shows: a conductor runs a script on each screen, in steps (every screen moves to step n together) or in tandem (screens run their own parts, with cues between them).
  • Sharing: in both modes, scripts, captured motions, recordings, data and other artifacts are shared with the mesh by default; the StudioGen where one was made can mark it private (then it stays there).

What this adds to the architecture

  • Roster: a signed, versioned list of members {device id, public keys, name, person, role (owner / member), may-invite, permissions}; each change signed by an owner (or, for joins, by the inviting member, countersigned by an owner when owners require it).
  • Invites: {mesh, inviter, expiry, single use, role offered} signed by the inviter; the pairing code carries the invite plus the mesh's relay list.
  • Artifact catalogue: each StudioGen announces its shared artifacts (id, kind, name, version, size, owner device); members fetch on demand over direct links or the relay (chunked), cache them, and see updates by version; private ones are never announced.
  • Conductor protocol (mesh mode): the conductor sends “prepare script S” (each screen fetches S if missing), then “step n” cues (steps mode) or named cues (tandem mode), with a shared clock (the conductor's time, offsets measured from hello round trips) so screens move within a few tens of milliseconds; screens report ready / done / failed.
  • Permissions: per device and per artifact or task kind (run scripts, run OS tasks, read data, drive the screen), checked by the device that would do the work.

Phases

  1. M1 Device identities (key pairs), mesh creation, invites, signed roster, presence; a DriveGen paired into a mesh sees every StudioGen by name.
  2. M2 Request mode: by device and by capability; permissions; StudioGen-to-StudioGen requests.
  3. M3 Shared artifacts: catalogue, fetch and cache, private flag, versions.
  4. M4 Mesh mode: the conductor, steps and tandem, shared clock, multi-screen sample show.
  5. M5 Owner-signed updates (relay list, roster), key rotation on removal, Nostr as a second relay family.

9. Questions that were asked

  1. Who's in it: only your own devices, or colleagues' too (a team mesh)?
  2. Who admits members: one owner StudioGen, any StudioGen, or any member with an invite?
  3. How changes reach members (new broker list, removed member): pair again in person (simplest, strongest), or an owner-signed update over the mesh (no re-pairing; you asked for re-pairing for broker changes)?
  4. What should flow: requests only (run, ask), or also shared things (scripts library, captured motions, data), and synchronised multi-screen shows?
  5. Permissions: per device (which scripts and tasks each DriveGen or StudioGen may run on which Mac)?
