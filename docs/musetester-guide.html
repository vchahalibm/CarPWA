MuseTester: using it, and writing tests

MuseTester is the apps' main tester. It works StudioGen, DriveGen, Workers and the mesh the way a person does: it clicks, types, scrolls and waits, and it checks what happens. This guide covers running it and writing new tests. Anyone who adds a feature to the apps also adds a test for it, so this guide is for them too.

1. What you need

  • Node.js 22 or newer (node -v).
  • StudioGen installed in /Applications, or the desktop app's files in the project: cd desktop && npm install. Use --app dev to test today's code from desktop/.
  • Google Chrome: it shows the control panel and runs DriveGen as a phone or an iPad.
  • Optional: Docker (OrbStack) for the Worker and StudioGBee tests.

Tests use a throwaway profile by default. Your own StudioGen, its sign-ins and its watchers are never touched. Only tests marked "profile": "mine" use your profile, and only when you pass --profile mine.

2. Running tests

node tools/musetester/muse.mjs                       # the panel, with every test
node tools/musetester/muse.mjs rpa watchers          # tests by id or tag
node tools/musetester/muse.mjs rpa-engine --go       # start at once, end when done
node tools/musetester/muse.mjs --silent              # no panel, windows hidden: for a run on its own
node tools/musetester/muse.mjs --list                # every test, its profile and tags
node tools/musetester/muse.mjs --record my-test      # you use the app; it writes the test
OptionWhat it does
--app installed|devThe installed StudioGen (the default), or the one in desktop/ with today's code.
--silentNo panel, StudioGen hidden, DriveGen headless, and steps that need you are skipped. Clicks and typing use page events.
--goWith the panel: the chosen tests start straight away, and MuseTester ends after them.
--speed 2Show mode twice as fast (0.5: half as fast).
--no-showThe windows are in view, but nothing is shown moving (no pointer and no real input).
--skip docker,slowLeaves out tests with these tags or ids.
--profile mineThe tests that need your accounts. Add --restart-mine to let MuseTester quit your StudioGen and open it again afterwards.
--keepLeaves StudioGen open after the tests, so you can look around.
--markTicks the try-it-out items in docs/TasksNeedingComeBack.md that passed.

3. The control panel

The panel opens in its own window beside the app. It lists the tests. Open one to see its steps, coloured as they run:

grey: to run   blue: running   green: passed   red: failed (its note says why, and a picture is taken)

  • Run all or Run on one test. In one go runs straight through. Step by step waits for Next step before each step.
  • When a step fails, choose Try it again (after fixing something by hand), Skip it, or Stop this test.
  • Steps only you can do (a drive, a tap on your phone) show Your turn.

Show mode is the default when the panel is open. A pointer glides to each target, rings it in blue and clicks it with real mouse input. Typing appears letter by letter, and a caption at the top names the test and the step. When a watcher checks, the agent browser's panel shows the page it reads.

4. One engine: RPA

Everything MuseTester does on the screen goes through RPA (js/rpa.js), the app's own automation engine. That covers clicking, typing, keys, scrolling, pointing, dragging, dropdowns, checkboxes, waiting and reading. Scripts use the same engine through the rpa.* actions, on Stage or anywhere. So a test that passes shows that the engine your scripts use works too.

WhereInput
StudioGen, show mode or a scriptReal input: Electron's sendInputEvent through DriveDeckDesktop.input. It is checked: a click on something that is covered fails and names what covers it.
StudioGen silent, and DriveGenPage events (pointer, mouse, click, input, change, keys).
A page of the agent browser (web)The webview's own real input; fields are found and focused through the bridge.

RPA never types into or records password, payment or one-time-code fields.

5. Your first test

A test is one JSON file in tools/musetester/tests/. Its id is the file name.

{
  "id": "settings-theme",
  "title": "Settings: the light theme is chosen through the screen and kept after a restart",
  "tags": ["settings", "ui", "rpa"],
  "steps": [
    { "do": "launch" },
    { "do": "view", "name": "settings" },
    { "do": "click", "role": "tab", "text": "System", "why": "Open the System tab" },
    { "do": "click", "text": "Light", "within": "Appearance", "why": "Appearance: Light" },
    { "do": "expect", "js": "document.documentElement.dataset.theme", "equals": "light", "why": "The screen turned light" },
    { "do": "quit" },
    { "do": "launch", "why": "Open it again (the same profile)" },
    { "do": "expect", "js": "document.documentElement.dataset.theme", "equals": "light", "why": "Still light" },
    { "do": "errors.none", "ignore": ["ResizeObserver"] }
  ]
}
  • Each step has do (what to do) and usually why, which the panel and the report show. Write it the way you'd tell a person.
  • on picks the app when there are several: studio (the default), phone, or a name given with as.
  • optional: true: a failure doesn't stop the test.
  • The steps stop at the first failure. cleanup steps always run.
  • ${name} in any value is a variable: from an earlier step's as, or from your muse.config.json.

This is a real test, tests/settings-theme.json. Run it: node tools/musetester/muse.mjs settings-theme --go. Then run it again with --silent. A good test passes both ways.

6. Finding things on the screen

Name things the way a person would. Every step that acts on something takes a target:

FieldFindsExample
textThe words on it: buttons, links, tiles, chips, tabs, menu items. An exact match wins over a starting one, which wins over “contains”. Of several, the tightest is taken (the button, not the card around it). Words that aren't on a control (a message, a status) are found too."text": "+ New watcher"
labelA field by its label, placeholder or aria-label."label": "Your name"
selA CSS selector. Use it when there are no words (an icon) or the words change."sel": "[data-wt=\"list\"]"
rolebutton, link, textbox, checkbox, combobox, tab… (with text to narrow it down)."role": "tab", "text": "Logs"
nthThe nth of several that match (from 1)."text": "Delete", "nth": 2
withinOnly inside something: a selector, or words (the part around them)."within": "#sheet"
sheet: trueShort for within: "#sheet", the open sheet.
Prefer words. "text": "Check and save" keeps working when the layout changes, and it reads well in the report. Use sel for icons, and data-* attributes where the app has them (data-wt, data-ag).

Code, when you need it

StepDoes
evalRuns js in the app's page; the value goes in as. Use it to set up (a board of controls, a setting) or to read state that isn't on screen. Without return the code is one expression; with it, a function body (await allowed).

Do things the way a person would (click, type, choose), and use eval for setting up and for looking. A test that clicks through the screens also tests the screens; one that calls the code directly tests only the code.

8. Checking results

expect checks one of these:

  • var: a variable, with dots for parts (check.hit.headline);
  • js: a value in the page;
  • sel: something shown on screen;
  • text: words anywhere on screen.

It checks with:

  • equals, contains, lacks, match (a regular expression), gte, lte;
  • none of them: the value must be true.

look, web.read, until and web.expect take the same checks. Other checks:

  • errors.none: no errors in the page (ignore lets known noise pass);
  • responsive: no hangs;
  • crash.none: no crash report;
  • log: the debug log says (or doesn't say) something.
{ "do": "look", "sel": "#status", "contains": "Saved", "as": "status", "why": "It says Saved" },
{ "do": "expect", "text": "New watcher", "why": "The button is on screen" },
{ "do": "expect", "var": "check.count", "gte": 1 }

9. Pages in the agent browser

Watchers and tasks work in StudioGen's agent browser. To act inside one of its pages, add web (part of the page's address) and use the web.* steps. A practice Slack test, for example:

{ "do": "launch", "practice": true },
{ "do": "practice.signin" },
{ "do": "web.click", "web": "slack", "text": "sales" },
{ "do": "web.type",  "web": "slack", "label": "Message", "text": "Hello", "enter": true },
{ "do": "web.read",  "web": "slack", "sel": "[aria-label^=\"Messages in\"]", "contains": "Hello" },
{ "do": "web.key",   "web": "slack", "key": "Meta+K" }

Use the practice sites (labs/practice/), never real accounts, for anything that sends.

10. Recording a test

node tools/musetester/muse.mjs --record watcher-pause --title "Pausing a watcher from its list"
  1. StudioGen opens with a throwaway profile, and a caption says it's recording.
  2. Use it as you would. Your clicks, typing (and Enter), dropdown choices and checkboxes are written down as steps, each by the words on what you clicked where they're unique, else its label, else a selector.
  3. Press Enter in the terminal. The steps are saved to tests/watcher-pause.json.
  4. Open the file and add what should be true: expect, look or wait.for after the steps that change something. Add why to each step. Then run it.

Password, payment and one-time-code fields are never recorded. Recording starts again from nothing if the page reloads.

11. The same engine in scripts

Scripts (and so Stage) drive the app with the same engine through these actions. The step's value is the target's words (or the text, for rpa.type), and args add the rest:

{ "do": "rpa.click", "value": "+ New watcher" }
{ "do": "rpa.type",  "value": "hello", "args": ["label=Message", "enter"] }
{ "do": "rpa.key",   "value": "Meta+K" }
{ "do": "rpa.scroll", "value": "", "args": ["to=bottom"] }
{ "do": "rpa.choose", "value": "", "args": ["label=Theme", "option=Light"] }
{ "do": "rpa.wait",  "value": "Saved" }
{ "do": "rpa.look",  "value": "", "args": ["sel=#status"], "as": "status" }
{ "do": "rpa.click", "value": "sales", "args": ["web=slack"] }

The actions are rpa.click, rpa.type, rpa.key, rpa.scroll, rpa.hover, rpa.drag (onto=), rpa.choose (option=), rpa.tick (off), rpa.wait (gone) and rpa.look. Args: sel=, label=, role=, nth=, within=, web=, and the flags double, right, enter, show (pointer and ring), slow. On Stage the pointer always shows. The test rpa-script runs such a script. More is in the scripts and tasks guide.

12. The rule: a test for every feature

Every new feature, or change in behaviour, comes with a MuseTester test in the same change. A fix comes with a test that would have caught the bug.
  1. Write the test (or record it, then add checks). Run it with --go and with --silent.
  2. Add it to tools/musetester/coverage.json under each part of the app it covers (js/<name>.js).
  3. Add its line to the library table in tools/musetester/README.md.
  4. If it covers a try-it-out item, put the start of that line in the test's tryitout, so --mark can tick it.

CI runs node tests/musetester-lint.cjs. It fails when any of these is true:

  • a test doesn't parse, or its id isn't its file name;
  • a test uses a step MuseTester doesn't have, or an rpa.* action js/rpa.js doesn't define;
  • a file in js/ isn't in coverage.json;
  • coverage.json names a test that isn't there.

Parts with no test yet are marked "todo" and printed as gaps on every run. "none" is for parts that can't have a test, such as the camera or a person in front of it, and must say why.

13. Results and the run log

Each run writes tools/musetester/reports/<time>/:

  • report.html: every step, its time, and pictures;
  • muse-log.md: the run log, written to be handed to Claude as it is. It has the machine and versions, each test's steps and failures, how long checks take per kind, the app's state after each test (watchers, agent-browser windows, storage, errors, performance metrics), a run book, and the debug log during the run.

The newest 10 runs are kept.

14. Tips and trouble

  • “is covered by …”: something lies over the target (a sheet, the agent browser's panel, a toast). Close it first, or wait for it with wait.for and gone.
  • “Nothing called … on the screen”: check the words (they are matched without regard to case), or narrow the target with within or nth. Run with --keep and look in the app.
  • Timing: don't add wait steps for the screen to settle. wait.for or until waits exactly as long as it takes.
  • Clean up: whatever a test makes in a real profile (watchers named “MuseTester …”) goes in cleanup.
  • Speed: --speed 3 while you write a test; --silent to check it holds without the pointer.
  • An app without rpa.js: MuseTester brings the engine from this checkout, so older installed apps still run the tests.
