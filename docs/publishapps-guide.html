PublishApps: building and publishing every app

One command builds, checks and publishes everything people use: DriveGen (the web app), NaoMuse (the Mac app), the NaoMuseHive image, the Worker image and the installer. It runs on your Mac, where the source lives, and nowhere else.

1. The idea in one picture

  your Mac                                               GitHub: vchahalibm/CarPWA (public)
  ────────                                               ──────────────────────────────────
  the source (readable, with history)                    main branch ── the website (DriveGen) ← GitHub Pages
        │                                                  tags w1000, w1001… ← big files, fetched by the apps
        │  PublishApps.mjs                                 release "updates" ── the signed feed NaoMuse follows
        ├─ 13 checks                                       releases v0.19.0… ── the DMGs to download
        ├─ a copy of the last commit, squeezed  ────────▶  ghcr.io: naomusehive, studiogen-worker images
        └─ the Mac app built and signed here

The source never leaves your Mac. What goes out is built from it, squeezed (and scrambled, if you choose), and only the parts that run.

2. Once, before the first run

  1. The signing key is at ~/StudioGen-update-keys/update-private.pem (already there). Without it the Mac app can't be updated: installed copies only accept updates signed with it.
  2. The signing certificate for the Mac app is in your login keychain (already there), so each version keeps the same identity and macOS doesn't ask for permissions again.
  3. The desktop's packages: cd desktop && npm install once.
  4. Permission to publish images: gh auth refresh -s write:packages once (done).
  5. Where it publishes is in tools/release/publish.json: vchahalibm/CarPWA. Installed apps already fetch from there, so it stays.

3. A run, step by step

installer/dist/publish-apps                   # with screens: you tick every part and option first
node tools/release/PublishApps.mjs --dry      # a practice run: everything except pushing
node tools/release/PublishApps.mjs            # the real thing, without screens
node tools/release/PublishApps.mjs --help     # every option

With screens: publish-apps

node installer/build.mjs --publisher makes installer/dist/publish-apps (same look as the installer). Run it in the repository. Ready shows whether everything is in place, with the fix for anything that isn't. Choose ticks each part (DriveGen, NaoMuse, NaoMuseHive, Worker, installer: ticked from what changed; ticking an unchanged one builds it anyway) and each option (practice run, scramble, skip the checks, keep the build folder, less output, ask before pushing, remember these as my defaults), plus the repository; ? explains each. Confirm shows the exact command it runs, and won't go while something a ticked part needs is missing. Then it runs it, shows each stage and the last lines, and asks you on its own screen before anything is pushed. "Remember" saves your options in tools/release/publish.local.json (not committed), which PublishApps reads as defaults too.

Without screens

What you see, in order:

  1. Is everything in place? The repository, the signing key, everything committed, gh signed in, and for the parts that need them: the token may publish packages, Docker answers, Go, the desktop's packages. Anything missing stops it here, before the checks, with the fix for each; nothing has been built.
  2. The plan. Each app with ✓ (it will be built) or – and the reason it won't (for example "its version is already published"), and whether the code will be squeezed or scrambled too.
  3. The checks, one line each with ok, about 25 seconds. A failure stops everything: nothing is published.
  4. A clean copy of your last commit, made in a temporary folder. Squeezing happens there; your working folder is never touched.
  5. The builds: the Mac app (a few minutes, only when its version went up), the installer (seconds), then the images (only when their files changed), for both processors into this Mac's Docker: they aren't pushed yet.
  6. The update feed, packed and signed with your key.
  7. "Publish all of this to vchahalibm/CarPWA? (yes/no)". Nothing has left your Mac until you answer yes.
  8. Publishing: Docker signs in to ghcr.io with gh's own token (no separate password), the images are pushed with docker push (each layer retried, up to three tries in all; what already reached ghcr.io is skipped, so a big Worker image over a home connection gets there), then the website, its tag, the feed, the DMGs, the installer.
  9. Checking what's live: it reads the feed back from GitHub and loads the website, to be sure they really changed.
It refuses to start with uncommitted changes. What ships is always exactly your last commit, so commit first.

4a. Trying a build on your Mac

Every run, practice or real, keeps what it built in the project's builds/ folder (never committed; the newest three are kept):

builds/w1001/
  site/                         DriveGen, exactly the files GitHub Pages will serve
  feed/                         the signed update feed
  NaoMuse-0.20.0-arm64.dmg      the Mac app (Apple silicon), when it was built
  NaoMuse-0.20.0.dmg            the Mac app (Intel)
  naomuse-install               the installer, when it was built
  build.json                    which commit, which versions, practice or published

Then:

node tools/release/PublishApps.mjs --dry      # build everything, push nothing
node tools/release/try.mjs                    # try the newest build (or: try.mjs w1001; try.mjs --list)
  • DriveGen: try.mjs serves the build at http://localhost:8090/. Open it in Safari or Chrome on the Mac. A phone on the same Wi-Fi can open the address it prints, though installing and offline use need https, so try those on the published site.
  • NaoMuse, without touching your own: it prints two lines. Open the DMG, then start the app from the disk image with an empty profile of its own (--user-data-dir=/tmp/naomuse-try). Your installed NaoMuse, its sign-ins and memory are untouched. Dragging it to Applications instead replaces your installed app, keeping your data.
  • Your installed NaoMuse taking it as an update: try.mjs also serves the signed feed at http://localhost:8091/. Quit NaoMuse and start it with STUDIOGEN_FEED=http://localhost:8091/ (the exact line is printed): it checks the signature as it does GitHub's and offers Restart now. Avatars it hasn't downloaded yet arrive only after the real publish.
  • The images, after a practice run, are in this Mac's Docker, ready for docker run.
  • The installer: builds/w1001/naomuse-install --check says what it would do on this Mac; without --check, the screens.

Happy with it? Run PublishApps.mjs without --dry: it builds the same commit again and publishes.

How often to publish is up to you: nothing runs by itself. A web-only publish takes about a minute and is how most changes reach people. Installed NaoMuse picks up a new web version on its own (Settings › System › Updates), and DriveGen on its next start.

7. The checks

Fourteen with Go on this Mac (thirteen without), the ones CI used to run, plus the installer building, vetting and passing its Go tests: the code parses; voice-command phrases; watchers; map watchers; lookahead; every part of the app has a MuseTester test; the names come from one place; the Handbook is current; every desktop file is packaged; the dark relay, the dark gate and the Node-RED link each attacked as a stranger would; the manifest is valid. Add a new one in CHECKS in tools/release/PublishApps.mjs.

MuseTester's full tests (which drive the real apps) are separate and slower: run them before a release you care about (node tools/musetester/muse.mjs --silent).

9. The rules that keep the source private

  • Never git push this folder to GitHub. The remote is named public-dist-do-not-push, and .githooks/pre-push refuses. PublishApps pushes from its own temporary copy.
  • Keys never go in the repository. .gitignore refuses *.key, *.pem, *.p12 and id_*. Keep keys in ~/StudioGen-update-keys/ or ~/.ssh/.
  • What was public stays public. The repository's history holds the source as it was until November 2026; only what comes after is private.

10. Backing up the source

Your Mac is the only place the source exists. Keep a locked copy elsewhere:

node tools/release/backup.mjs --set-pass     # once: your own passphrase (four or five unrelated words)
node tools/release/backup.mjs --upload       # an encrypted copy of every branch and commit, in the public repo
node tools/release/backup.mjs --restore <file> <folder>     # getting it back

It's AES-256, so the copy is only noise to anyone else. Keep the passphrase in your password manager: nothing can open a backup without the passphrase it was made with.

11. When something goes wrong

It saysDo this
You have uncommitted changesCommit them, then run it again.
A check FAILEDIts output is printed under it. Fix that, commit, run again. Nothing was published.
desktop/node_modules is missingcd desktop && npm install
The feed was not signed / no signing keyThe key must be at ~/StudioGen-update-keys/update-private.pem.
An image failed to build or pushIs Docker (OrbStack) running? Then gh auth refresh -s write:packages. A 403 asking ghcr.io for an "anonymous token" meant Docker wasn't signed in to ghcr.io; PublishApps now signs it in with gh's token before pushing.
The worker image didn't push (failed to copy … Put https://ghcr.io/…)The upload of its big layers broke off. Run it again: what reached ghcr.io isn't sent again, so each run gets further. A steadier connection (cable rather than Wi-Fi) helps.
publish-apps stays on “Checking what is now live”A publish-apps from before 16 Nov 2026 kept PublishApps waiting on its question’s pipe after everything was published (the feed and site were already live). Ctrl-C is safe then; the current one ends by itself.
Checking what's live: "not yet"GitHub takes a minute or two. Run curl -sL https://github.com/vchahalibm/CarPWA/releases/download/updates/update.json | head later.
Something published that shouldn't have beenPublish again from a commit that fixes it: the newest feed wins, and the website is replaced each time.
