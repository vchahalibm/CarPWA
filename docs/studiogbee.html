1. The rule: what is private, what is shared

A StudioGen is its owner's agent. Its sign-ins (Outlook, Teams, Slack, WhatsApp…) and personal data are for its owner only. Everything else it can do is what the mesh is for.

Kind of actionableWho may run itExamples
Needs a sign-in or personal data (“only my devices”)The owner's own devices only: their paired phones and iPads, and the StudioGens they marked as theirs. Never another member, whatever the mesh roster says.Unread mail, Teams and Slack chats, WhatsApp, calendar, sending anything as the owner; tasks in a signed-in container; AppleScript/Shortcuts/shell on the Mac; the Mac's databases
SharedAny mesh member, when the owner shared it (the task's or script's Share tick), unless the owner blocked that member (Mesh › Devices).Web search, flight status, prices, capturing data from public web pages, Stage presentations and shows, scripts

A task needs a sign-in when it opens {outlook} {teams} {slack} {whatsapp} (or those sites' addresses), runs in a container other than Default, runs an os.* or data.sql step, or runs another task that does. The task editor shows the result and lets the owner tick Only my devices by hand too (never the other way round: a task that opens a sign-in site stays private). A shared script is checked the same way before it runs for someone else.

2. Who is asking: my devices

Every request arrives through a channel only one device can use, so StudioGen knows who sent it without trusting what the request says about itself:

ChannelProvesCounts as mine
Pairing room (relay, the SG3… code)the device that scanned the code (only it has the room's key)yes: pairing is shown only to your own devices (“Anyone who can scan this code can pair”)
Direct link set up through a pairing roomthe same deviceyes
Direct link by QR both ways (no relay)the device in front of the Macyes
Mesh pair room / mesh direct linka mesh member (its ECDH key)only if this StudioGen lists it under My devices: automatically when it is a paired device's mesh identity, or ticked by the owner (e.g. their second StudioGen)

My devices is kept on each StudioGen, not in the mesh roster: the mesh owner signs the roster, so if the roster decided, a mesh owner could add their own phone as “yours”. Mesh › Devices › Yours shows and changes them (paired devices are always yours); unticking takes effect at once.

3. Profiles: an owner's sign-ins

  • A profile is one of the owner's accounts kept signed in: a container of the agent browser (Default, Work, Personal, or new ones) with the sites it is for. One person, many profiles (“Work”: Outlook, Teams, Slack; “Personal”: WhatsApp).
  • One profile lives on exactly one StudioGen. An owner may have several StudioGens (a Mac and a StudioGen Worker in Docker), each holding different profiles; a request goes to the one holding the profile for its site. Sign-ins are never copied between machines (they are locked with that machine's key, and sites distrust moved sessions).
  • Stored: cookies and site data in the container's own folder inside StudioGen's data folder, encrypted with the key in “StudioGen Safe Storage” (Keychain; in a Worker, a container secret). Profile names and sites are ordinary settings. Passwords are never stored.
  • Each StudioGen announces, in its mesh presence, the names of the sites its profiles cover, to its owner's devices only, so their phones know where to send what.

4. Signing in: at the Mac, then remotely

  1. At the Mac (first choice): as today, the task stops, the Mac shows the sign-in page in the agent browser, and the phone says “Sign in to Outlook on your Mac”.
  2. Remotely (second): the phone offers “Sign in from here”: the agent browser's page is shown live on the phone over the direct link (pictures one way, taps and typing the other, end-to-end encrypted). Two-factor codes on the phone just work. The password goes straight into the page and is never recorded or kept; this screen is the only thing that may type into a password field, and only what you type live. Needs a direct link (relays are too slow for a live picture); a StudioGen Worker can only be signed in this way.

5. StudioGBee: the optional always-on hive

Without StudioGBee everything works as now: StudioGens and DriveGens find each other through the relays and direct links. StudioGBee adds an always-on place for when you want requests and cards to wait instead of failing.

What it does

  • Queue: requests for a StudioGen that is offline; cards for a requester that is offline
  • Who's around: presence and which StudioGen serves what, even while every Mac sleeps
  • Push: “your card is ready” to DriveGen (Web Push; iPhone home-screen apps support it)
  • Backup: a sealed copy of the mesh roster and of each owner's task library, so a new Mac can recover them
  • Dashboard for mesh owners (section 7)
  • TURN (optional, off unless switched on): carries a connection when hole punching fails

What it never does

  • Hold sign-ins or run tasks
  • Read what it carries: requests, cards, backups are sealed end to end with keys the mesh already has (pairwise ECDH, the group key); StudioGBee sees “sealed, from A to B, expires 10:12”
  • Decide who is in the mesh: the roster stays signed by its owners

Shape

 DriveGen ──sealed request──► StudioGBee (team A) ◄──── federates ────► StudioGBee (team B)
    ▲                          queue · presence · push · backup · dashboard · TURN (opt.)
    │ card: direct, or                │  (Docker anywhere, or a Cloudflare Worker)
    │ queued + push                   ▼
    └──────────────────── owner's StudioGen (Mac, or Worker in Docker): fetches its queue on coming online,
                          runs, sends the cards back (direct if the requester is reachable, else via StudioGBee)
  • Hosting: one codebase, two ways: a Docker container (a VPS, a NAS, a Mac) or a Cloudflare Worker with a Durable Object (no machine). A page can't receive connections, so StudioGBee is a small server process, not a PWA.
  • Run by a team, optional: a mesh lists its StudioGBees (like its relays); with none, nothing changes.
  • Federation: StudioGBees join separate teams' meshes. Each team keeps its own roster; a person in two teams' meshes is reached through either StudioGBee, which forwards sealed messages addressed to device ids it doesn't host to the StudioGBee that does.
  • Connecting: devices keep using the relays and direct links (WebRTC with STUN: hole punching through home routers) as the main way; StudioGBee's WebSocket is one more path; its TURN is an option in Settings › Connections, used only when nothing else connects (strict routers, mobile networks).

6. Waiting requests and when they go stale

When the StudioGen a request is for is offline, the request waits: on StudioGBee when there is one, else on the asking device while it is open. Each request carries its own rule, chosen by the asker (who, for anything private, is the owner):

KindWait at most (default)Then
Email (Outlook)10 mingive up and say so
Teams10 mingive up
Slack10 mingive up
WhatsApp10 mingive up
Calendar10 mingive up
Web and other10 mingive up
Acting (send, reply, book), any site10 minask me again before it runs, if it waited

Each kind: “don't wait”, a number of minutes, or “until it comes online”. Asked in the startup checklist of both apps (“When your Mac is offline…”), changed later in Settings › Agent › Waiting requests.

7. The StudioGBee dashboard

For mesh owners. A high-level view of the mesh built only from the metadata that flows through (who, to whom, kind, size, timing, status, path); never contents, which StudioGBee can't read anyway. Login: the owner's browser joins as a viewer device once (scan a QR code from StudioGen), then a passkey (Face ID / Touch ID) unlocks it; the roster's owner signature is what makes it an owner's view.

8. StudioGen Worker: StudioGen in a container

  • StudioGen's own code on Linux in Docker (Docker on a Mac first), headless (a virtual screen): the agent browser, containers, tasks, scripts, the mesh, the bee.
  • Not there: Apple's on-device model (AI steps use Claude with a key, or Ollama), Apple speech, AppleScript/Shortcuts, the Keychain (the key that locks sign-ins comes from a Docker secret).
  • Signed in only remotely (section 4). Some sites ask for extra checks from data-centre addresses; at home on Docker for Mac this doesn't arise.
  • Its owner pairs it like a phone, so it is one of their devices; it holds its own profiles.
